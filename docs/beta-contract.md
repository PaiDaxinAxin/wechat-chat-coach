# Internal beta contract

Status: implemented; the new followup, timing, immutable-case and field-coach paths have synthetic contract tests. Earlier bounded Agnes integration does not establish real chat effectiveness. Personal project; 2026-10-01. External access is a separate delivery gate in the acceptance matrix.

The application has a direct local demo and a retained invited-user mode. The owner currently deferred email, login and public authorization work and requested one simulated WeChat thread with inline AI advice and day/night themes. The same server owns profiles, conversation history, quotas, calls, untrusted feedback and review. Every provider call contains the complete current source knowledge and all approved supplements. No client bundle contains knowledge or credentials.

## User journey

Local demo opens a fixed fictional profile and conversation with no login or onboarding barrier, using a dedicated private database. It stays loopback-only and disables login, registration, management and HTTP MCP routes. Edits survive reload and restart. Server startup and persistence alone never call a provider. The UI analyzes an eligible complete context once on opening or after a new counterpart message; after free classification exhaustion it requests a direct reply instead. Persisted attempts include running and failed jobs, so reload does not automatically retry a failed call. A deliberate retry creates a new request ID.

In retained invited-user mode, an owner issues a single-use free or paid-beta invite. Registration stores a password hash and creates an isolated account. The user fills a short custom questionnaire and real background/style/growth goals; paid accounts may fill the full questionnaire. The user creates counterpart records with meeting channel, app profile or offline scene, previous rounds and background, then pastes counterpart messages into the simulated WeChat thread. Suggestions are editable and copyable. Pasting the next message atomically associates the captured prior draft and records an unknown, nonconsenting raw observation. That prior draft has `inferred_from_followup` provenance; the application does not verify that it was sent. The UI has no separate sent-confirmation or feedback button. Each message is editable/deletable; concrete meeting arrangements have their own state. The header selector marks the three strongest supported interactions. Explicit negative resistance recommends pausing. No display-profile or offline course is included.

The three direction percentages are uncalibrated recommendation weights, not success probabilities. The same classification may include `fieldCoach` to identify the current topic, repetition/closure, active leadership and an A/B/C warming layer without an extra call. A round means a complete topic; 10–20 messages are a checkpoint, not a mandatory topic switch. A is a shallow sincere evaluation or definition, B a male-to-female romantic frame, and C a clear private/intimate implication. Established mutual comfort is a prerequisite for C, not its definition. The user may explicitly ask the side coach to assess a plan; that output is separate from a WeChat reply.

Free classification has three lifetime successful context analyses. A replay of the same context or switching direction does not consume another classification trial. Failed classifications do not consume successful classification trials. Reserved concurrent calls cannot overspend remaining trials. After exhaustion, generation runs directly without a classification call or fabricated weights. Paid-beta access is owner-granted for testing; this is not a payment processor. Both tiers have configurable bounded provider-call budgets that count started attempts, including provider failures.

## API shared by web UI and server

### Personal style learning

`GET /api/style-learning` returns only the authenticated account's revision, private rules and bounded expression cases. Case source identities link to the immutable originating suggestion/job without exposing the full job snapshot or knowledge. The user's own version is a draft/self-report, not confirmation of WeChat sending. Whether a linked counterpart response has been recorded is an independent, unassessed observation; no outcome is inferred.

The existing `PUT /api/profile` accepts an optional `styleLearning` mutation with `requestId`, `expectedRevision`, an optional `review` and an optional `ruleChange`. The review names an owned counterpart and suggestion and includes `ownVersion`, `why`, `reasonKind`, `styleFit` and `willingness`. Rule changes are `propose`, `adopt`, `adopt_new` or `revoke`. Rules distinguish `current_preference` from `growth_goal` and preserve text, conditions and limits; unspecified conditions do not claim universal effectiveness. Replacement creates a new rule version using `supersedesId`. Only an explicit adoption activates a rule.

Profile, style case, rule status, audit and request receipt commit atomically. Revision checks protect against stale updates; identical request/body replay does not duplicate a case or adoption, and a changed body with the same ID conflicts. Ordinary profile updates remain compatible and participate in revision protection. Style mutations do not invoke a model. Only adopted abstract rules and their effective identity enter subsequent account-owned contexts; candidates, ratings, case texts and observations stay private and excluded. Original style, growth goals and complete selected questionnaire remain separate. Historical model inputs stay immutable; changing effective preferences changes future cache identity. Stopping one rule does not restore an old profile. Deleting a counterpart removes its private style cases and source links; independently adopted personal preferences remain manageable.

The account MCP retains its four existing tools and no profile/rule-writing authority. Its inference path reads the same server-selected active rules. This personal-preference path never promotes untrusted external feedback, writes shared knowledge or trains model parameters.

All JSON responses use `{data: ...}`; failures `{error: {code, message}}`. Cookies carry the session; mutations also require `x-csrf-token` from `/api/me` and same-origin requests. Register/login are same-origin and rate limited. No client-supplied role, plan or user ID grants authority.

- `GET /api/meta` → `{name, questionnaires: {short, full}, localDemo:{enabled,synthetic}, privacy}`. Each questionnaire item: `{id, text, dimension, reverse?}`; choices 1–5.
- Local demo only: `POST /api/demo/session` with the strict empty object `{}` creates the fixed fictional session and returns `{user,csrfToken,counterpartId,synthetic:true}`. Caller identity fields are rejected. Ordinary invited mode returns 404. Loopback socket, Host, Origin and proxy-header checks precede session creation.
- `POST /api/register` `{invite, username, password}` → session and `{user, csrfToken}`.
- `POST /api/login` `{username,password}` → `{user,csrfToken}`; `POST /api/logout`.
- `GET /api/me` → `{user:{id,username,plan,role},csrfToken,profile,quota:{classificationRemaining,providerRemaining}}`.
- `PUT /api/profile` `{background,style,growthGoals,relationshipGoal,questionnaire:{kind:'short'|'full',answers:{[id]:1..5}}}` → `{profile}`. Full answers rejected for free users.
- `GET /api/counterparts` → `{counterparts:[{id,alias,channel,rounds,updatedAt,heat}],topThree:[id]}`.
- `POST /api/counterparts`; `PUT /api/counterparts/:id`: `{alias,channel:'app'|'offline'|'other',appProfile,offlineScene,background,rounds}` → `{counterpart}`.
- `GET /api/counterparts/:id` → `{counterpart,messages,suggestions,currentSuggestionIds,classification,heat,meeting,jobs,directReply,modelContext,latestCoachPlan}`. `currentSuggestionIds` contains owned suggestions whose immutable base-context identity matches the current conversation; it exposes IDs, never private snapshots or knowledge. Existing `pendingEligible` remains the durable use/consumption check. An eligible copy additionally exposes `pendingCopiedAt`; the UI only restores an old-context draft by default if it was explicitly copied after the latest incoming record. Legacy cases without a matching snapshot remain viewable as history. `directReply` is the current default reply or null; `modelContext:{classificationAttempted,directReplyAttempted}` reflects any persisted current-context attempt, including failures. `latestCoachPlan:{plan,planAssessment}` is returned only for the current context or null. Historical suggestions do not establish a current result. `DELETE` cascades the user's conversation, jobs, suggestions, feedback and copy/followup receipts.
- `POST /api/counterparts/:id/messages` `{speaker:'self'|'other',text}` → `{message}`; `PUT /api/counterparts/:id/messages/:messageId` same body; `DELETE` removes it. New/changed context invalidates stale judgments.
- `POST /api/counterparts/:id/followup` `{text,requestId,previousSuggestionId?,previousReplyText?,previousCopyReceiptId?}` → `{message,previousMessage,feedback,timing,cached}`. A suggestion ID requires the captured editable draft; a copy receipt requires that suggestion. With a prior draft, one transaction writes an inferred self message, the counterpart message, a `raw_untrusted` receipt with unknown outcome/consent false, and the idempotency receipt. Without a draft it writes only the counterpart message. Identical requests replay; changed payload under the same request ID returns 409. The same suggestion/draft and quoted response replay their original receipt even under a new request ID; reuse with a different response returns 409. Do not attach an already consumed suggestion to every subsequent pasted sentence.
- `POST /api/counterparts/:id/suggestions/:suggestionId/copied` `{requestId,copiedText?}` → `{copyReceipt:{id,suggestionId,copiedAt,provenance:'clipboard_copied'},cached}`. Called after a successful clipboard action; the server records receipt time, not verified WeChat sending. A new actual copy uses a new request ID. Followup uses a matching receipt/text; edited text falls back to the weaker suggestion-preparation time. Unknown or reversed clocks do not produce an invented delay.
- `PATCH /api/counterparts/:id/messages/:messageId/timing` `{actualWechatAt:ISO_datetime|null}` → `{message}`. Past user-reported WeChat time is optional and editable; `recordedAt` remains immutable. Display/analysis prefer `wechatTime.at` when present and retain `source:'user_reported'`. Only a self→other pair with both annotations yields `user_reported_interval`; otherwise the recorded copy/preparation estimate remains weaker. Changing either speaker or deleting its pair clears derived interval links. Timing edits invalidate current model judgments but do not trigger an automatic paid call or rewrite historical snapshots.
- `POST /api/counterparts/:id/classify` `{requestId}` → `{classification,heat,cached,quota}`; no provider call when quota is unavailable.
- `POST /api/counterparts/:id/reply` `{requestId,direction?:'up'|'down'|'sideways',intent?}` → `{suggestion:{id,reply,reason,action,styleNote,direction,knowledgeHash},cached,quota}`.
- `POST /api/counterparts/:id/coach-plan` `{requestId,plan}` → `{planAssessment,cached,quota}`. Assessment is `{verdict:'suitable'|'adjust'|'wait'|'needs_context',reason,timingSuggestion:{status:'now'|'after_response'|'after_topic'|'wait'|'unknown',guidance,evidenceIds},adjustedPlan?,nextAction}`. Adjustment is required only for `adjust`; unknown timing has no precise countdown or evidence IDs. One explicit call uses the shared daily provider budget, no classification trial, and creates no chat suggestion or transcript message.
- Compatibility/internal only: `POST /api/counterparts/:id/sent` `{suggestionId,actualSentText}` → `{message}` records a user-confirmed sending claim. The new UI does not require this step; it never sends to WeChat or verifies platform delivery.
- `PUT /api/counterparts/:id/meeting` `{status:'none'|'proposed'|'alternative'|'confirmed'|'declined',time,place,note}` → `{meeting}`. Confirmation requires time and place.
- Compatibility/internal only: `POST /api/counterparts/:id/feedback` `{suggestionId,actualSentText,counterpartReply,observation,kind:'positive'|'pitfall'|'uncertain',consent:boolean}` → `{id,stage:'raw_untrusted'}`. No raw submission enters model context or source knowledge. Automatic inferred followup receipts remain quarantined when cleaned and cannot be promoted to knowledge, evaluation or training, even if a later manual sending record exists.
- Owner only: `GET /api/admin/feedback`, `POST /api/admin/feedback/:id/clean`, `POST /api/admin/feedback/:id/review` `{decision:'approve'|'reject',purpose:'knowledge'|'evaluation',conditions,limits,note}`. Cleaning preserves raw data and records transformations/missing evidence; approval requires a cleaned, permitted candidate, reviewed conditions and limits. Review is not model-parameter training.
- Owner only: `POST /api/admin/invites` `{plan:'free'|'paid'}` → `{invite}`; `PUT /api/admin/users/:id/plan` `{plan}`. Never expose these to testers.
- Owner only: `POST /api/admin/users/:id/mcp-token` → one per-account, expiring token; issuing another revokes the previous token. The account MCP at `/mcp` exposes only counterpart listing, classification, reply and feedback; it shares stored contexts, object ownership and persistent quotas with the UI.

## Persistence and exposure

Use one Node.js 26 server and SQLite database in an ignored/private data directory, with transactional quota reservations and per-account object ownership. Runtime and backup files are never published to GitHub. The build assembles only public assets; a private server installation includes the source knowledge. Deployment requires a controlled personal host, persistent volume and TLS. Owner stdio MCP remains available locally; restricted MCP retains its limited interface.

Fresh model reservations write immutable private snapshots of the complete model input, profile/object revision, meeting, request intent/plan, direction and available classification weights, model/context/protocol identity, and knowledge hash/version. The complete source used for each call is archived once under private `knowledge-versions/<hash>.md`; clients receive neither its text nor a file endpoint. Owner feedback review may inspect the original private case. Old jobs with no snapshot are explicitly `legacy_incomplete`; today's profile is never backfilled into an old case. Cache identity includes the full context, knowledge hash, operation/options, context/protocol version and provider model. Replays preserve the original source job, not a new observation.

`recordedAt`, `wechatTime`, interval sources and inferred provenance pass through domain validation and native model input. Slow replies are one signal among five heat dimensions, never a fixed one-hour/half-day score rule. Whether the counterpart explains a delay is assessed from actual text, with missing explanation unknown. Raw feedback remains isolated from all model prompts. Immutable raw/case snapshots retain the original timing when the editable history is later corrected.

Verification covers the direct thread → automatic once-per-context analysis → chosen editable reply → copied receipt → next pasted message path, explicit plan assessment, two-account isolation, paid/free permissions, transactional replay/concurrency/rollback, failure recovery, restart persistence, complete knowledge input, owner cleaning/review, snapshot immutability and original-byte preservation. Synthetic cases prove workflow reliability, not real chat effectiveness. Account MCP continues to expose only listing/classification/reply/feedback; it has no owner, full-text, case-export, followup, time-edit or plan tools.
