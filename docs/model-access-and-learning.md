# Model access, open-source scope and reviewed improvement

Status: current product decisions and next-stage specification, updated 2026-10-01. The owner chose MIT code and CC BY 4.0 knowledge, then clarified two delivery modes: official hosting using our AI provider and backend, or independently operated open-source deployments. The official website includes three successful AI replies per day for free accounts and a separate paid tier. Removing per-account BYOK from the website never meant removing free official access. This document does not itself enable public access, payments, new data processing, donations or training.

## Owner direction

- Organize and clean user conversation data to improve the assistant over time, described by the owner as RSI/self-iteration.
- Official website users use our server-configured AI provider. Free accounts receive three successful sendable replies per day, with paid access as a separate tier. Store service records in our backend; these records may be a source for cleaning and reviewed improvement under the data-purpose controls below. Do not build hosted BYOK, user-key settings or per-user provider routing for the website.
- Open-source users operate their own deployment, provider credentials and data. They pay their provider or infrastructure operator, with no required software payment to this project and no automatic central transcript upload. Managed hosting/support for their instances is outside our delivery scope. Voluntary appreciation remains optional.
- Welcome community improvements through PRs reviewed by the owner. Self-hosting does not require contributing changes; a contribution does not grant production access.
- Preserve the existing complete-context and reviewed-knowledge approach. The owner explicitly replaced the earlier core-knowledge secrecy requirement with full publication of code and knowledge. This does not authorize publication of private conversations, profiles, account credentials or runtime records.

Open source permits commercial use and sale; charging only for the official service is a product choice, not a condition imposed by open source. See the [Open Source Initiative FAQ](https://opensource.org/faq#selling). The repository contains the complete knowledge in current files and Git history; that content is intentionally in release scope. License scope is recorded in [LICENSING.md](../LICENSING.md). All reachable release history needs inspection for private data and credentials before visibility changes.

## Goals and boundaries

The official service has one provider path with free daily reply allowances and paid entitlements. Retain the ordinary paste-and-reply interaction, and improve reviewed rules using evidence with explicit permitted purposes. Self-hosting reuses the same open source with deployment-owner configuration; it is not a second mode inside our hosted account settings. Preserve complete selected knowledge and recorded context rather than silently truncate them to fit a cheaper model.

The first improvement loop changes reviewed cases, prompts, rules and evaluations. It does not retrain model weights or autonomously deploy its own changes. We do not describe collection alone as learning. Official-backend storage and its role as a potential improvement source are now owner-approved product direction. Before public launch, specify and implement user-facing purposes, data choices, retention/deletion and access controls; payment collection still needs its provider, prices and implementation. Source publication does not authorize production deployment or publication of personal records.

## Accepted open-source scope and provider boundary

There is an unavoidable boundary: the endpoint receiving a full prompt receives the full knowledge. A user-controlled endpoint can simply record it. Even with an allowlisted endpoint, prompt visibility depends on the user's provider account and provider logging. Keeping the HTTP request on our server does not by itself hide that prompt from the provider/account owner. Output filtering and MCP restrictions cannot prevent exposure at the input endpoint.

The owner chose open code plus open complete knowledge after this limitation was explained. One public codebase supports deployment-owner configured compatible models and the full public framework. On our website, we are the deployment owner and supply the official AI service for both free and paid tiers. Self-hosters configure their own instance independently. Official hosting adds managed model service, not a secret version of the core game framework. Do not create a restricted replacement knowledge base or a parallel closed-core product.

Prepare a reviewed public release from approved code/content, including fixtures, screenshots, prompts, documents, generated assets, source maps and dependency notices. Excluding a file from the latest tree does not remove it from Git history. Inspect all relevant history before making the existing personal repository public. Keys, real chat/profile records, private contributions and deployment configuration are excluded. Public code does not make the live owner workspace or administrative APIs public.

Community members may propose code fixes, terminology clarifications, counterexamples, evaluation cases and knowledge changes. Proposals should include provenance and applicability. Public issues/PRs use fictional or safely publishable examples only; do not solicit raw private conversation dumps. Maintainers review changes before adoption. Source openness neither proves a submitted case true nor grants permission to centralize users' local chats.

The owner further specified that community changes must arrive as PRs and receive his review; contributors cannot push to the official production service. `.github/CODEOWNERS` assigns review to PaiDaxinAxin. Protect the default branch with required checks/review and no force pushes; production authorization is a separate owner action. See [CONTRIBUTING.md](../CONTRIBUTING.md). Existing CI contains no deployment job or real service secrets.

## Proposed official-service and self-hosting contract

- Official requests use our server-configured provider and the authenticated account's free allowance or paid entitlement. Clients cannot supply an endpoint/key, choose another account, change a payment plan or obtain the server credential. Local/self-hosted deployment owners configure their own provider privately; no official balance or hosted connection registration is involved.
- First support the existing compatible chat/function-result transport, not a claim of compatibility with every API. Check structured output, full-context capacity and image capability separately. A text-only model can still handle text; screenshot analysis must explain the missing capability rather than silently bill another model.
- Keep provider credentials in the deployment's private environment/secret store, never in conversation records, audit fields, URLs, browser storage or export bundles. No hosted vault for customer-supplied keys is needed. Official provider changes are operator-controlled; self-hosters control their own providers.
- Include account and provider/model configuration revision, knowledge version and protocol revision in job/cache identity. Do not reuse a result across accounts or after a relevant configuration change solely because a model name matches. No raw key or reversible secret enters a cache key or snapshot.
- Self-hosted calls incur no charge from this project and do not use its official keys. Existing beta plan flags and trial counts are local product controls, not an upstream billing or license-verification dependency. Do not add phone-home enforcement or automatic hosted-service fallback to independent deployments.
- Free official accounts receive three new successful sendable `reply` results per Asia/Shanghai calendar day across all counterpart records. Reserve slots atomically before dispatch and settle using the reservation date, including completion after midnight. Cached/idempotent results, failed calls and wait/pause results without a sendable reply do not consume successful-reply slots. Release reservations once on failure or recovery; retain the independent cost budget for started provider attempts. Paid and owner accounts are exempt from this three-reply cap, not from provider budgets.
- The existing three lifetime successful classification trials remain independent. Exhausting classification trials permits a direct reply only while its daily allowance remains. Direction changes can create a new reply and therefore consume a reply slot; selecting a direction does not itself consume another classification trial. `coach_plan` and `image_read` retain their provider-attempt limits and do not consume reply slots. Do not describe three replies as three unrestricted model calls or promise unlimited free auxiliary calls.
- Capability or context failures remain explicit. Complete knowledge/history is not truncated to conceal an unsupported model, and retries must not silently incur duplicate charges.
- Official usage receipts identify route, operation, model, knowledge version, provider-reported usage when available and charge state. Unknown usage is not zero. Requests, callbacks and retries must not double-charge; ambiguous provider outcomes require reconciliation, not blind retries.

## Coaching interaction and annotations

Show 上切 / 下切 / 平移 choices only when changing topic or when the user explicitly requests a change. Ordinary continuation, receiving a reply, waiting and pausing do not require selecting a direction. Preserve the distinction between topic movement, relationship action and A/B/C warming intensity. Any shown percentages remain uncalibrated recommendation weights; unresolved Game 4.0 values, stage transitions and weights are interview questions, not adopted policy.

Users can add, edit or clear a private annotation on an owned message. Keep it separate from the original text, speaker, timestamps and provenance. Complete-context requests include the annotation with `source:'user_annotation'`; it is the user's interpretation, not verified counterpart intent or a system instruction. Changing it invalidates future context/cache identity without rewriting immutable previous model snapshots or automatically invoking a model. An annotation is neither proof that a reply was sent nor consent to research, publication or model training.

## Contribution and reviewed improvement

The owner has selected official-backend storage for website conversations and independently operated data for self-hosted users. Website records are a candidate source for reviewed improvement. This resolves where data lives; it does not make all stored data a public contribution or parameter-training permission. No new upload path is planned for self-hosted instances. A self-hoster may voluntarily contribute a safely publishable example through the existing PR process.

For records permitted for improvement under the implemented user-facing data policy, use one admission path:

`official service record → purpose-authorized raw candidate → cleaning/quarantine → owner-reviewed candidate → held-out evaluation → explicit release`

Each admitted record needs a versioned purpose/permission receipt with account, scope and time. Explain official storage, internal improvement and any optional wider sharing in the account-level data policy/settings before launch; do not add a confirmation step to every message. Knowledge improvement, evaluation, public case publication and future parameter training are distinct purposes; approving one does not authorize the others. Payment or a donation alone is not a receipt for every data use. Remove unnecessary counterpart identifiers before a case enters a shared dataset. Existing `consent:false` records remain ineligible for promotion under the current contract; do not retroactively relabel them based on this owner planning decision.

Cleaning should retain enough context to judge the whole topic and background while removing contact information, names, precise locations, account identifiers and unnecessary sensitive details. Use consistent pseudonyms within the case so that removing identifiers does not reverse speakers or destroy sequence. Preserve uncertainty, actual/user-corrected timing provenance, which advice was offered, which wording was actually recorded, what was inferred, and which response was observed. Uploaded images remain transient under the current contract; no future image training use is implied by screenshot support. Model-assisted cleaning produces candidates only and must use a route permitted for that data purpose.

Reuse current provenance/deduplication/quarantine primitives. Extend cleaning to the full contributed context, not merely the short outcome fields. Keep positive, negative and unknown outcomes; no reply or a single emoji is not a verified failure. A copied draft is not verified delivery. Inferred follow-ups retain their uncertainty and cannot be laundered into confirmed training evidence. Do not restore a mandatory “confirm sent” or “record feedback” button in normal chat to make the dataset look cleaner. Evidence review belongs in the optional contribution/reviewer workflow.

For each proposed rule change, retain source cases, conditions, counterexamples, uncertainty, knowledge/prompt/model versions and affected behavior. Use a fixed held-out set separated by conversation and person, so parts of one interaction do not appear on both sides. Evaluate complete-context use, style fit, correct boundaries and appropriate reply/wait decisions as separate outcomes. The system's own heat score is not an independent success label, and an unselected alternative has no observed counterfactual result. Do not optimize on an asserted real-world intimate outcome or treat model agreement as proof of causation.

The owner releases a reviewed candidate only after evaluation, using the existing version/CAS safeguards. Keep a previous release available for rollback; any regression or withdrawn source must stop admission into new releases. Autonomous prompt changes, automatic KB promotion and model-parameter training remain off in this first stage.

Withdrawal must stop new collection/promotion promptly, block stale queued workers using the consent revision, and remove eligible contributed raw/cleaned/export copies according to a documented retention policy. Private-conversation deletion and contribution withdrawal are separate visible actions. Track lineage into candidate datasets and knowledge versions. Existing immutable archives and append-only supplements cannot truthfully promise immediate erasure; implement invalidation/redaction and retention handling before opening external contribution. Do not promise reversal of third-party processing or already-trained model weights.

## Delivery sequence and acceptance

1. **Scope resolved; launch details remain:** official hosting offers the free daily reply allowance and a paid tier using our provider/backend; self-hosting uses the operator's own model/data. Keep one MIT/CC BY code-and-knowledge distribution. Specify pricing, the personal payment provider and user-facing data policy before enabling the relevant public service.
2. **Official model access:** reuse deployment-owner provider configuration and implement account entitlements. Prove with isolated two-account and cross-instance tests that cache entries, reply reservations and jobs do not cross accounts, concurrent jobs cannot exceed three free replies, Shanghai midnight does not lose or double-charge a reservation, failed/non-sendable/cached results do not consume reply slots, and all provider operations retain their bounded budgets. Verify complete-context/capability failures and that clients cannot replace the official provider. Verify self-hosted operation has no official-key or central-upload dependency.
3. **Improvement admission:** prove zero shared-queue visibility or model-assisted research calls without the required purpose permission, revoked permission blocks queued work, deletion/withdrawal handles derived copies, and inferred outcomes stay unverified. Keep operational coaching storage distinct from research admission.
4. **Reviewed improvement:** compare a candidate with the current version on a frozen set, record coverage and unknowns, reject boundary regressions and demonstrate release/rollback. Add real provider tests only with a bounded authorized call count; synthetic tests are not evidence of better real conversations.
5. **Official service launch:** verify official billing and an optional personal appreciation link before making either available. The licensed source and full knowledge can be published independently after their file/history review; publication does not need to wait for billing or authorize production access.

Initial measurable gates are zero successful free replies beyond the daily allowance, zero provider calls outside their operation-specific budgets, zero charges or automatic central uploads for independent self-hosters, zero shared research admissions without their required permission, zero cross-account/cache/secret exposure in the acceptance cases, and a source receipt plus release record for every promoted rule. Report model success rate by provider/capability, failure cost, unknown-outcome coverage and cost per successful operation. Adoption, donation conversion and actual coaching improvement have no baseline yet; do not invent percentage targets or claim improvements from collection volume.
